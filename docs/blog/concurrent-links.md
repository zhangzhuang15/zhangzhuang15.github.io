# 写在最前面

有一次听到隔壁同事聊到某公司使用 4 台 8G 4core 的服务器，支撑 1 亿的并发量，我感到非常好奇，
4 台服务器真的可以做到嘛，太离谱了吧。于是，我就想搞清楚一个问题，一台服务器最多支持多少
个 TCP 连接？

## TCP 连接数

如果不知道如何区别两个 TCP 连接是否为同一个，那么在估计连接数的时候，就会有问题。

一个 TCP 连接如何被唯一地确定呢？

参考了一部分博客，我了解到：`一个套接字对唯一标识了一个TCP连接`。

套接字对就是`(源IP地址，源端口号):(目标IP地址，目标端口号)`。

如果有两个 TCP 连接，上述四个要素中有一个不同，那么这两个就不是同一个 TCP 连接。

根据套接字对分析，理论上一个服务进程最多可以支持多少个 TCP 连接？

这里假设服务器只有一个 IP 地址，服务进程只监听一个端口号。

那么最多连接数就是 2^(32 + 16).

> IP 地址是 32 bit 位，端口号是 16bit 位。

## 理论很多，实际达不到

理论上看，服务进程可以支持非常多的连接，但实际上是做不到那么多的，最大的限制因素就是服务器的内存。

当服务进程启动后，它会生成一个套接字 A，监听一个端口号。当有客户端连接时，服务进程会生成一个新的套接字，
该套接字负责和客户端完成数据通讯，同时这个套接字会复用套接字 A 的端口号。

问题是，每个套接字是一种数据结构，会占用内存，它要把数据传送给客户端，需要占用一部分内存作为网卡数据的
缓存。这些都是内存开销。网上有博客说，在套接字不发生数据传输的情况下，也需要占用 3k 左右的内存，我们不妨
基于这种说法，做进一步推断，假设套接字需要使用 4k 的数据缓存，那么一个套接字就要占用 7k，每有一次连接，
就形成一个套接字，那么 100 万连接的话，占用的内存是 100*0000 * 7k = 1000 \_ 7M = 7G(用 1000 近似估计
1024， 不严格使用 1024 计算内存单位的转换)。

也就是说，一个 8G 内存的服务器最多支持 100 万连接，那么 4 台最多就支持 400 万连接，所以支持 1 亿连接是不对的。

但是，如果一个连接上处理 25 个请求（长连接情形），那么 4 台服务器可以支持 1 亿请求量。

上述假设中，数据缓存区是 4k，在一定范围内，这个值越大，网络传输中读写数据越快，那么一个连接处理 25 个请求
的时间开销就越少，但我们假定的是 4k，也就是说，虽然支持单连接处理 25 个请求，但这 25 个请求处理完毕不一定
很快。

## 关于连接的补充

### 地址复用（SO_REUSEADDR）

使用`socket`编程，默认不开启地址复用选项。

TCP 用 四元组 唯一标识一条连接：

```txt
(源IP, 源端口号, 目标IP, 目标端口号)
```

如果两个 tcp socket 绑定同一个本地端口，来了一个连接请求，系统不知道该交给谁——歧义，所以默认禁止。

服务重启时端口被占用，是一个特殊的问题。

```txt
服务崩溃了 -> 服务处于 TIME_WAIT 状态 -> 原来的tcp连接没有断开 -> ip地址和端口号依旧被占用

不修改原来的ip地址和端口号，服务重启 -> 发现地址和端口依旧被占用 -> 报错，address already use
```

开启`SO_REUSEADDR`，就不会有上述问题了。但是重启后的服务存在隐患，因为是卡在旧连接 TIME_WAIT 状态启动的，服务可能会收到旧包并处理，这是数据污染。不过概率很低，一般的服务都会开启`SO_REUSEADDR`。

### 端口复用（SO_REUSEPORT）

开启这个选项后，允许多个进程/线程绑定同一个端口，内核做负载均衡，每个连接分配给一个 socket。

```txt
进程1: bind(8080) + SO_REUSEPORT ✓
进程2: bind(8080) + SO_REUSEPORT ✓
进程3: bind(8080) + SO_REUSEPORT ✓
→ 内核把连接轮流分给三个进程
```

用途：多进程服务器（如 Nginx worker 进程）性能优化，避免单个 accept 队列成为瓶颈。

真实的风险：

- 连接不均衡：内核的分配基于四元组 hash，某些 IP 段的请求可能全堆到一个进程
- 进程崩溃丢连接：某个进程挂了，分配给它的连接直接断掉，没有平滑迁移
- 惊群问题没有完全消除：多个进程同时被唤醒处理一个事件，虽然比不用 REUSEPORT 好，但仍存在

### 何为连接

都说 tcp 连接，但连接并不是指物理上的连接，而是通信双方各自维护的一组状态信息：

```txt
客户端内存里：
{
  本地IP: 192.168.1.1,
  本地端口: 54321,
  远端IP: 1.2.3.4,
  远端端口: 443,
  状态: ESTABLISHED,
  发送缓冲区: [...],
  接收缓冲区: [...],
  序列号: 12345,
  ...
}

服务端内存里：
{
  本地IP: 1.2.3.4,
  本地端口: 443,
  远端IP: 192.168.1.1,
  远端端口: 54321,
  状态: ESTABLISHED,
  ...
}
```

TCP 连接是靠双方的状态机+序列号，在无序的网络上制造出"有序可靠传输"的幻觉。

你和服务器"建立了连接"，然后把网线拔掉。

物理层面：什么都没发生，TCP 不感知;

TCP 状态：双方还是 ESTABLISHED，以为连接还在,等到有数据要发，发不出去，超时重试几次后，TCP 才认为连接断了;

这说明连接的存在与否，完全由双方的状态决定，不是由物理介质决定。

### TIME_WAIT 说的是哪一方，为什么要有

主动关闭连接的一方，才会进入到 TIME_WAIT 状态。

主动关闭的情境：

- 服务端或者客户端主动调用`close`
- 服务端或者客户端进程崩溃，操作系统帮忙`close`
  > 如果立即断电，导致服务端崩了，操作系统也崩了，服务端没有主动关闭。这个时候，客户端在多次发送数据没有得到回应后，客户端会主动关闭。

```txt
主动关闭方（A） 被动关闭方（B）
│ │
│──── FIN ──────────────>│ A说：我要关了
│<─── ACK ───────────────│ B说：收到
│ │ （B可能还有数据要发）
│<─── FIN ───────────────│ B说：我也关了
│──── ACK ──────────────>│ A说：收到
│ │
TIME_WAIT CLOSED
（等待 2MSL）
```

为什么要等这段时间？

两个原因：

- 防止最后一个 ACK 丢失。A 发出的最后一个 ACK，B 可能没收到。B 会重发 FIN。如果 A 已经关闭了，B 的重发得不到响应，B 就无法正常关闭。TIME_WAIT 期间 A 还在，能重发 ACK。
- 防止旧数据包污染新连接。网络中可能还有这条连接的旧数据包在游荡（被某个路由器延迟了）。等 2MSL 能保证这些"幽灵包"全部消失，再复用这个端口不会被污染。2MSL 一般 1 到 4 分钟。

处于 TIME_WAIT 状态的一方，收到"幽灵包"时，直接舍弃，但是收到 FIN 包，会重发 ACK 并重置 2MSL 倒计时。

### http1.1 和 http2 的本质区别

http1.1: 在没有收到 request A 的响应之前，无法发送 request B;

http2: 同一个 tcp 连接，在没有收到 request A 的响应之前，仍然可以发送 request B;

http2 在应用层增加了流的概念，对发送的包做了特殊处理，不用干等着来保证响应返回的正确顺序。但 http2 仍有缺陷，如果 http 包文被切割成多个 tcp 数据包发送，且其中一个 tcp 数据包丢了，那么就要等待 tcp 数据包重传，期间就没办法接收 http 响应了。http3 改用 udp 协议，解决了这个问题，丢包就丢了, 不用重发，不用等。

> 主流的浏览器已经支持 http3，浏览器会自动从响应头中识别出服务端是否支持 http3，并在下一次发送请求的时候，采用 http3 协议

### 吞吐量大，延迟为什么也大

`服务处理的请求数 = 吞吐量 * 延迟`。

吞吐量：单位时间内处理多少请求；

延迟：收到请求到返回响应，需要多少时间。

吞吐量增大后，意味着有很多请求被放在了队列中，那么这些请求不会被立即处理，自然延迟就会增大。
